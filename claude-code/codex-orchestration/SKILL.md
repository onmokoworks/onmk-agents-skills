# Codex オーケストレーション

Claude Code は指揮役に専念し、実装は Codex CLI（`codex exec`）のワーカーに任せます。ワーカーは1チケットにつき1つの git worktree で動き、終わったら決まった形式の報告を書きます。指揮役は報告をうのみにせず、自分で確かめてからマージする、という分担です。

## 仕組み

```
orchestra/
  BRIEF.md          全ワーカーに最初に渡す共通の決まり（templates/BRIEF.md から作る）
  tickets/<ID>.md   1チケット1ファイル（templates/ticket.md から作る）
  queue.txt         実行する順に ID を並べる。後から行を足せば拾われる
  state/<ID>.meta   開始と終了の記録。消すとそのチケットをやり直す
  logs/<ID>.log     ワーカーの出力
worktrees/<ID>/     ワーカーの作業場所（ブランチ orch/<ID>）
```

`orchestra/` と `worktrees/` は `.gitignore` に入れます。報告はワーカーの worktree の `orchestra/reports/<ID>.md` に書かれます。

スクリプトは `scripts/` にあります。どれもプロジェクトのルートで動かすか、`ORCH_MAIN` にルートのパスを入れて使います。

| スクリプト | 役目 |
| --- | --- |
| `queue.sh <model\|-> <queue-file> [並列数]` | キューを読み、空きがあれば次のチケットを起動し続ける。メモリとディスクに余裕がないときは待つ |
| `run.sh <ID> [model]` | worktree を作り、BRIEF とチケットをつないで `codex exec` に渡す。通信エラーで落ちたら再開させる |
| `watch.sh` | ワーカーの終了、ルール違反、エラーが新しく出るまで待って、出たら表示して終わる |
| `status.sh` | チケットごとに1行で状態を出す（経過時間、報告の status、コミット数） |
| `drift.sh` | 動いているワーカーのルール違反を出す（`/tmp` への書き込み、push や履歴の書き換え、保護されたファイルの変更、同じコマンドの繰り返し） |
| `procguard.py` | Python のプロセス数かスワップが上限を超えたら、いちばん大きいワーカーを止める |

## 始め方

1. `templates/BRIEF.md` を `orchestra/BRIEF.md` にコピーし、`<PROJECT: ...>` の部分を埋める。正しさの基準（テスト、比較の相手）と、触ってはいけないファイルを必ず書く。
2. `.gitignore` に `/orchestra/` と `/worktrees/` を足す。
3. 最初のチケットを数本書き、ID を `orchestra/queue.txt` に並べる。
4. キューを Bash のバックグラウンドで起動する（`run_in_background`）。
   `ORCH_BASE=<統合ブランチ> scripts/queue.sh - orchestra/queue.txt 3`
5. 必要なら `procguard.py` もバックグラウンドで起動する。

並列数はマシンのメモリと1ワーカーの重さで決めます。16 GB の Mac で、ビルドとテストが重い作業なら3〜5本が目安です。

## チケットの書き方

- 1チケット1目標にする。迷ったら分ける。
- 「いまの状態」に、事実と証拠（コミット、ファイル、失敗するコマンドと出力）を書く。前のチケットで試してだめだったことも書く。
- 「終わりの条件」はコマンドと期待する結果で書く。
- 前のチケットのマージが必要なら `depends: <ID>` を書く。キューは、そのブランチがマージされて消えるまで待つ。
- ID が `I` で始まるチケット（統合作業）は、ほかが全部止まってから1本だけで動く。
- push や保護されたファイルの変更など、BRIEF で禁止していることをさせるときは、チケットに「誰がいつ許可したか」を書いて明示的に許す。

## 回し方

1. `watch.sh` をバックグラウンドで動かし、終わるのを待つ。終わったら、その出力が次にやることの合図になる。
2. `status.sh` で全体を見る。違反が出ていたら、該当のログの末尾を読む。
3. 終わったチケットの報告を読む。
4. 報告の `verify` にあるコマンドを、自分で実行して結果を確かめる。報告の数字だけで判断しない。
5. `git diff <統合ブランチ>...orch/<ID>` を読む。テスト用の入力だけに合わせた分岐、許容誤差を足して通したテスト、期待値の書き換えがあれば差し戻す。
6. 問題なければ統合ブランチで `git merge --no-ff orch/<ID> -m "Merge <ID>: <一行>"` し、`git worktree remove` と `git branch -d` で片付ける。
7. `blocked` や `partial` なら、分かったことを「いまの状態」に書いた次のチケットを作ってキューに足す。同じチケットをそのまま回し直さない。
8. 区切りのいいところで全体のテストを回し、通ったら push する。

ユーザーへの報告は短くします。何がマージされたか、何が止まっているか、次に何をするかだけを書きます。

## 守ること

- キューを止めるときは、`queue.sh` の zsh プロセスだけを kill する。バックグラウンドのタスクごと止めると、動いているワーカーまで道連れになる。
- `git stash` は使わない。stash は全 worktree で共有されている。
- 指揮役もメインのチェックアウトを汚さない。マージと片付け以外の作業は worktree でする。
- push、PR、リリースなど外に出る操作は、ユーザーの許可を取ってからにする。許可したことはチケットに書く。
- 報告がないまま終わったワーカーは、ログの末尾で理由を確かめてから、やり直すか分けるかを決める。

## うまくいかなかったこと

- 大きすぎるチケットは、途中で文脈が尽きて `partial` で終わりやすい。1〜2時間で終わる大きさに分けると通りやすい。
- 「直して」だけのチケットは、テストの入力に合わせた場当たりの修正が返ってきやすい。BRIEF の規則3と、差分を自分で読む手順が効く。
- ワーカーが一時ファイルを `/tmp` に書くと、並列で動くほかのワーカーと衝突する。scratch を worktree の中に決めておく。
- パスに空白があると、ビルドツールによっては失敗する（QEMU の configure など）。BRIEF に回避策を書いておく。
